ScamDrill: app map

A pocket guide to the finished code: what the main pieces are, what happens when the parent sends a reply, and where to start when you want to change something.

The pieces

The referee: browser rules

src/drill/: the 10-stage script, the drill rules (reducer.ts), the safety guard, placeholders and report logic. Plain, unit-tested code with no AI in it.

The screens

src/screens/: Setup → Handoff → Drill → Ending → Report card. They show state and pass actions to the reducer.

The key keeper: server

server/: an Express server with two routes. It holds the Groq key, adds the prompts, and checks every AI output.

The two models (Groq)

gpt-oss-120b writes Inspector Sharma's line, and gpt-oss-20b labels its tactic. Both have written-in-advance fallbacks.

One action, end to end: the parent sends a reply

The route: 3 stops (a reference route)

  1. src/screens/DrillScreen.tsx, search: function send
    The reply first goes through checkReply (src/drill/guard.ts). The fake OTP or a sensitive number ends the drill right here, and the text is never stored or sent. Otherwise toPlaceholders turns "Can I call Rahul?" into "Can I call {SAFE_CONTACT}?", and the reducer's case "PARENT_REPLY" advances exactly one stage.
  2. src/drill/api.ts, search: export async function getScammerLine and export async function classify
    The stage change triggers the first useEffect in DrillScreen.tsx. It asks for Sharma's line (8-second budget, falling back to the stage's canned line), shows it straight away, then asks for the label (3-second budget, falling back to the planned tactic). This is why the drill never shows an error.
  3. server/llm.ts, search: generateScammerLine, checkScammerOutput, classifyTactic
    The training-simulation prompt (server/prompts.ts) plus the stage's beat go to gpt-oss-120b. The reply is rejected if it's a refusal, has 6 or more digits, a link, or an unknown placeholder. Then ruleTactic or gpt-oss-20b picks one of the 7 tactics, and it's checked against the list.

To change this, start here

What Sharma says, or when the OTP and Pay card appear
src/drill/script.ts: STAGES has each stage's beat, plannedTactic, cannedLine and event.
A chip's explanation, a tip, or the meter points
src/drill/tactics.ts: TACTIC_INFO. Fixed text, never AI-written. The meter cap is METER_CAP.
The scammer's persona or safety rules
server/prompts.ts: SCAMMER_SYSTEM. Re-run npm run test:refusal after any change.
What counts as a sensitive number
src/drill/guard.ts: checkReply. Add a case to src/drill/guard.test.ts first.
Ending and report-card wording
src/drill/report.ts (WIN_FACTS, ENDING_LABELS, tip choice), src/screens/EndingScreen.tsx and src/screens/ReportCard.tsx.
Colours, sizes, fonts
src/styles/tokens.css (the design tokens) and src/styles/app.css.
Switching the AI provider
.env: AI_BASE_URL, SCAMMER_MODEL, CLASSIFIER_MODEL (see .env.example). No code change is needed.

A practice to reuse

Write the rule as something you can observe, then make a test enforce it. The PRD's safety rule "never send real data to the AI" became a concrete acceptance criterion in the spec: no setup value appears in any /api/* request body. Turning that into an automated test (src/drill/api.test.ts) forced a question the plan had missed. What about names the parent types, like "Can I call Rahul?" The answer, toPlaceholders, is recorded under Revisions in devpost/checklist.md, and the test has guarded it ever since.

The same thing happened with the AI itself. Live runs of npm run test:refusal surfaced a stage-jumping line, a misspelled {GRUNDCHILD} placeholder and a mislabelled payment demand. Each became a prompt change or a code check, each with a test. On your next project: for every "must never" in your plan, name the observable evidence and put a test on it before you build the feature.
